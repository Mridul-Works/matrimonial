 THE ADMIN IS AN OVERSEER, NOT A PARTICIPANT
-------------------------------------------------------------------------------

 Every other account is a normal member: a browsable profile that sends and
 receives interests. The admin is deliberately outside that:

   - has NO profile, and never appears in anyone's browse results
   - CANNOT send an interest - no buttons anywhere, on any page
   - has no "My Matches" or "My Profile" (an "Admin" link replaces them);
     typing /matches redirects to /admin/matches, /my-profile to /admin
   - enforced SERVER-SIDE too: the interest action checks the role and
     refuses admin sessions, so even a hand-crafted form POST creates
     nothing (verified: interest count unchanged after a forced POST)

 The admin observes everyone's activity and registers walk-in members.

-------------------------------------------------------------------------------
 STEP 1 - LOG IN AS ADMIN                                             [ /login ]
-------------------------------------------------------------------------------

 admin / admin  ->  redirected straight to /admin (members go to /profiles).

 Access is checked twice, independently:
   1. proxy.ts - a fast cookie check at the edge; bounces anonymous visitors.
   2. requireAdmin() inside each admin page - the real gate; re-verifies the
      session AND the stored role. A member typing /admin lands on /profiles.

-------------------------------------------------------------------------------
 STEP 7 - REGISTER A MEMBER                              [ /admin/profiles/new ]
-------------------------------------------------------------------------------

 For WALK-IN registrations, where a family gives their details in person.
 Because every profile belongs to an account, this creates BOTH - the member
 can then log in themselves and send interests.

   +-----------------------------------------------------------+
   |  Register a Member                                        |
   |                                                           |
   |  Full Name *                                              |
   |  Username * (their login)  |  Temporary Password *        |
   |  Gender *  | Date of Birth * | Height                     |
   |  City *    | Profession *                                 |
   |  Educational Qualification (one per line)                 |
   |  Work Experience                                          |
   |  Brother(s) | Sister(s)                                   |
   |  Partner Preference                                       |
   |  [            Register Member            ]                |
   +-----------------------------------------------------------+
                     ( * = required )

   submit
     |
     +--> username taken / missing field -> error under that field
     |
     +--> valid -> account + profile created together
                   code number assigned automatically
                   -> back to the Profiles tab
                   -> immediately visible to every other member

 The code number is NOT entered by hand - it is generated from the highest
 existing number, so duplicates can't happen.

 The Server Action re-checks admin rights before writing, so a non-admin
 cannot register anyone even by posting the form directly.

===============================================================================
 BACKEND HOOKS - where a real database plugs into this flow
===============================================================================

 STEP 3  overview        -> getAllUsers() + getProfiles() + getAllInterests()
                            + findMutualPairs(interests)
 STEP 4  match activity  -> interests.ts  getAllInterests()
                                          findMutualPairs()
 STEP 5  profiles table  -> profiles.ts   getProfiles()
 STEP 6  members table   -> users.ts      getAllUsers()
 STEP 7  register member -> users.ts      createUser()
                            profiles.ts   createProfileForUser() + updateProfile()

 Admin screens join users + interests in memory. With a real database those
 become one query per screen; the page components stay as they are.
 findMutualPairs() is a pure function - in SQL it is a self-join on interests.

 SUGGESTED SCHEMA WHEN MIGRATING
 -------------------------------
   users      ( id, name, username, password_hash, role, created_at )

   profiles   ( id -> users.id PRIMARY KEY,      <- 1:1 with the account
                code_no UNIQUE, name, gender, dob, height_label, city,
                education[], profession, work_experience, family[],
                partner_preference, photo_url, created_at )

   interests  ( id,
                from_user_id -> users.id,
                to_user_id   -> users.id,
                created_at )
                UNIQUE (from_user_id, to_user_id)  <- makes the toggle safe
                CHECK  (from_user_id <> to_user_id) <- no self-interest

   -- mutual matches, as a query:
   SELECT a.from_user_id, a.to_user_id, GREATEST(a.created_at, b.created_at)
   FROM interests a
   JOIN interests b ON a.from_user_id = b.to_user_id
                   AND a.to_user_id   = b.from_user_id
   WHERE a.from_user_id < a.to_user_id;   -- each pair once
